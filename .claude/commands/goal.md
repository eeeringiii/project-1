依頼: $ARGUMENTS

いきなり実装に入らないでください。雑な一言をそのまま目標にすると、走り出してからズレます。
次の順番で進めてください。

## 1. 調査（先に手を動かさない）
依頼に関係する現在の実装を読む。OSHICOA の場合、最低限このあたりを疑う:

- 診断ロジック・スコアリング: `lib/diagnosis/index.ts`, `data/questions.ts`
- タイプ定義・コピー: `data/types.ts`, `data/tags.ts`, `data/phases.ts`
- 状態: `stores/diagnosis.ts`
- 画面: `app/` 配下の該当ルート
- シェア画像: `app/api/og/route.tsx`

見えている UI だけを直して終わりにしない。source of truth がデータ側にあるなら、そちらを直す。

## 2. 目標を明文化する
調査結果をふまえて、次を短く言語化してから実装に入る:

- **ゴール**: 何がどうなったら完了か（ユーザーから見た状態で書く）
- **触る範囲**: 変更するファイル
- **触らない範囲**: 特に「4軸の診断モデル・スコアリング・重み・タイブレーク・タイプコード」を変えるのかどうかを明示する。変えないなら「変えない」と書く
- **確認方法**: `npm run lint` / `npm run build` に加えて、どの画面をどの幅で見るか

依頼の解釈が複数あって結果が大きく変わる場合だけ、ここで一度確認を取る。
そうでなければ前提を明記して進める。

## 3. 実装
明文化した目標のとおりに、一連の変更をまとめて入れる。表面的な 1 箇所で止めない。

## 4. 完了報告
`npm run lint` と `npm run build` を通したうえで、
「やったこと / 触らなかったこと / 確認した画面」を短く報告する。
落ちているなら落ちていると言う。
